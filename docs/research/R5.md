# R5 — Memory-bandwidth and cache stressors for E1

**Recommendation (IMPLICATION):** use `--stream` for sustained bandwidth pressure, `--cache` with explicit sizes for cache-pressure sweeps, and `--memrate` for a traffic-rate sweep. These approximate the papers’ interference mechanisms; they do not reproduce their benchmarks or establish Cortex-A76 worst-case bounds. Keep E1 on the stock Linux target, consistent with PROJECT.md §§5–7; RT-Gang/MemGuard installation is outside this ticket.

## SOURCE — what the research establishes

| Source and exact location | Evidence relevant to E1 |
|---|---|
| [DeepPicar, author-hosted revised text](https://www.ittc.ku.edu/~heechul/papers/picar-rtas2018-revised.pdf), §IV-A; §IV-D, Fig. 10; §IV-E, Fig. 11 and footnote 3; Appendix B | Pi 3 uses Cortex-A53 and a shared 512 KB L2. The interference experiment puts one DNN on core 0 and 1–3 IsolBench writers on other cores, specifying `-a write -m 16384`. It reports up to 9.6× slowdown without a comparable increase in L2 misses, supporting a memory-latency explanation rather than cache capacity alone. Appendix B documents frequency changes from temperature/power problems. |
| [RT-Gang, arXiv v1](https://arxiv.org/html/1903.00999v1), §II, Fig. 1; §§III-D, IV-F; §§V-A–C | Separate cores still interfere. The synthetic experiment uses two 384 KB working sets against Pi 3’s 512 KB shared cache; the DNN experiment uses BwWrite with twice-LLC working sets. Its mitigation combines gang scheduling with hardware-counter-driven bandwidth throttling. Evaluation platforms are Pi 3 and TX2, not Cortex-A76. |
| [MemGuard](https://www.ittc.ku.edu/~heechul/papers/memguard-rtas13.pdf), §§III-A–B, IV-A–B; §V-A, Table I; §V-D | On Core2Quad, sequential independent accesses achieve much higher bandwidth than dependent random pointer chasing. The design assumes private/partitioned LLC; experiments deliberately reduce cache-capacity interference. Per-core budgets use counter interrupts and scheduler enforcement. LLC-miss accounting omits writeback traffic and requires attention to prefetching. |
| [Raspberry Pi documentation, “BCM2712”](https://www.raspberrypi.com/documentation/computers/processors.html#bcm2712) | Pi 5 has 512 KB private L2 per core and a 2 MB shared L3. Pi 3’s shared-L2 experiments therefore cannot be transferred by retaining their original buffer sizes. |

**IMPLICATION:** E1 should vary working-set size and co-runner count independently. Cross-core cache pressure targets the shared L3; thrashing a separate core’s private L2 does not directly evict the victim’s L2. Larger buffers introduce both cache misses and DRAM traffic, so “cache-only” and “bandwidth-only” would overstate isolation. Paper slowdown factors and MemGuard’s bandwidth budgets are not Pi 5 predictions.

## SOURCE — verified stress-ng interface

The [upstream V0.17.06 manual](https://github.com/ColinIanKing/stress-ng/blob/V0.17.06/stress-ng.1), sections **“STREAM memory stressor,” “Cache stressor,” and “Memory read/write stressor”**, documents:

- `--stream-index 0`: sequential copy/scale/add/triad; `--stream-l3-size` overrides cache-size discovery, not total allocation. Index 3 adds shuffled indirection, not dependent pointer chasing.
- `--cache-size`, `--cache-level`, and `--cache-no-affinity`: select buffer sizing and suppress the stressor’s affinity changes. The manual warns that cache stressing is not intelligently tuned to every cache geometry.
- `--memrate-bytes`, `--memrate-rd-mbs`, `--memrate-wr-mbs`: buffer size and requested read/write rates; actual rates depend on execution conditions. Default operation cycles through supported access widths.

**IMPLICATION:** avoid x86-only cache flush/fence options on A76. Do not treat `--memrate` as a write-only BwWrite equivalent, its rate controls as MemGuard reservations, or stress-ng throughput as a standardized STREAM benchmark.

## IMPLICATION — proposed E1 profiles

Use one inference thread on CPU 0 and the bridge on CPU 1; add stressors on CPU 2, then CPUs 2 and 3. This experimental placement separates CPU scheduling competition from cross-core interference; it is not a production threading decision. Keep placement identical in the baseline. Launch **one independent stress-ng invocation per stress core**, giving each cache invocation its own allocation. Run profiles separately.

Commands below show CPU 2; repeat concurrently with `-c 3` for two co-runners. All commands are for **Ubuntu ARM64 on Pi 5**, not macOS.

| Profile | Command | Purpose / limitation |
|---|---|---|
| B0 | No stress-ng process | Baseline with the same victim configuration. |
| B1 | `taskset -c 2 stress-ng --stream 1 --stream-l3-size 2M --stream-index 0 --timeout 70s --metrics-brief` | Sequential bandwidth pressure beyond LLC; mixes reads, writes and arithmetic. |
| C1 | `taskset -c 2 stress-ng --cache 1 --cache-level 3 --cache-size 2M --cache-no-affinity --timeout 70s --metrics-brief` | Repeat at `256K`, `1M`, `2M`, `4M`, `8M`: compare below-private-L2, L3-scale and beyond-L3 footprints. Sizes do not guarantee residency or eviction. |
| B2 | `taskset -c 2 stress-ng --memrate 1 --memrate-bytes 64M --memrate-rd-mbs 500 --memrate-wr-mbs 500 --timeout 70s --metrics-brief` | Repeat at 500, 1000 and 2000 MB/s per direction per worker; omit both rate options for an unrestricted case. These are requested rates, not measured DRAM bandwidth. |

Optional locality contrast: repeat B1 with `--stream-index 3`; label it mixed random-access/cache pressure, not MemGuard’s latency benchmark.

**Validation before accepting profiles:** record `stress-ng --version`, installed package version, kernel, cache topology, exact commands, model/thread count, and CPU affinities. Confirm options with the installed manual; the reference above pins interface semantics, not the target’s installed version. Warm up for 10 seconds, measure the remaining 60 seconds, and repeat each condition at least five times in shuffled order. Record inference p50/p95/p99/max, deadline misses, bridge dispatch jitter, achieved stressor rates, CPU frequency/temperature, major faults and swap activity. Reject or separately label thermally throttled/paging runs.

Use available, documented target PMU events to compare victim cache refills and execution stalls against B0; A76/DSU event availability and mappings remain **[unverified]**. Generic cache-miss counts times line size do not establish total DRAM bandwidth. Accept a bandwidth-saturation claim only with measured traffic/scaling evidence; otherwise report “bandwidth-oriented stress.” Report cache pressure as mixed contention unless measurements distinguish it. Observed maxima remain measurements, not proven WCET bounds.
