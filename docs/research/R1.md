# R1 — System-Level Simplex: supervisor recommendations

Context: `PROJECT.md` §§1–6 and `AGENTS.md` read. Scope: Pi 5/Ubuntu + STM32F446RE/FreeRTOS, UART, simulated failsafe output. Research checked 2026-10-06; recommendations below are design proposals, not hardware-verified results.

## SOURCE — full-text findings

**1. Bak et al., “The System-Level Simplex Architecture for Improved Real-Time Embedded System Safety,” RTAS 2009, pp. 99–107.** Full author-uploaded text read. The decision module and safety controller form the trusted core, isolated from the complex controller’s processor/OS. Missing timely commands select the concurrently available fallback. The pendulum switches before leaving its Lyapunov stability neighborhood; the pacemaker checks rate limits and rate smoothing. [Full text, §2, §§4.1.1, 4.2](https://www.researchgate.net/publication/221569245_The_System-Level_Simplex_Architecture_for_Improved_Real-Time_Embedded_System_Safety).

The fault model includes unsafe values, NaN/infinity, absent output, and shared-resource failures causing crashes or timing faults. Sensors, actuators, safety hardware, synthesis correctness, and environmental-model errors remain assumptions/exclusions. Architectural checks cover resource isolation, type validation, and data flow: complex commands go to the decision module, not the safety controller. [Same full text, §§2.1, 3.3](https://www.researchgate.net/publication/221569245_The_System-Level_Simplex_Architecture_for_Improved_Real-Time_Embedded_System_Safety).

**Latency evidence:** Table 1 lists successful injections including wrong-way maximum voltage, no output, OS crash, timing faults, and reboot. Figure 6 records one destabilization/recovery episode; reboot testing establishes continued stability. **No numerical fault-to-detection or detection-to-output latency, dedicated latency instrumentation specification, or latency distribution is reported.** [Same full text, §§4.2.1–4.2.2, Table 1, Fig. 6](https://www.researchgate.net/publication/221569245_The_System-Level_Simplex_Architecture_for_Improved_Real-Time_Embedded_System_Safety).

**2. Mohan et al., S3A, arXiv:1202.5722v1 (2012).** Full 15-page preprint read. A trusted FPGA combines plant-state checks with a timing FSM; unexpected messages and execution/period violations trigger fallback. It assumes predictable periodic tasks and trusted monitoring hardware. [Full text, §1 assumptions, §§3, 5.2, 5.4.6](https://arxiv.org/pdf/1202.5722v1).

**Measurement:** `rdtsc` profiles repeated executions with empty-loop overhead subtraction; interrupts are disabled, cores partitioned, and a sibling core disabled. Extra arithmetic loops mimic injected code. FPGA arrival intervals over thousands of iterations capture execution plus PCIe jitter. [Same preprint, §§5.4.3–5.4.5, 6.1–6.3](https://arxiv.org/pdf/1202.5722v1).

**0.6 µs is timing-deviation sensitivity, not failsafe latency.** The reported **5.7 µs detection window** is the FSM’s maximum allowed wait from a control-start message, incorporating measured jitter. It is not a separately instrumented fault-to-physical-safe-output distribution. Table 2 gives plant-state-only detection as 10,000 µs; §6.3 instead says five 50 Hz iterations = 100 ms. This discrepancy is unresolved. Timing spoofing and broad timing ranges limit detection. [Same preprint, §6.3/Table 2, §7](https://arxiv.org/pdf/1202.5722v1).

**3. Bak et al., “Real-Time Reachability for Verified Simplex Design,” RTSS 2014, pp. 138–148.** Full 11-page author PDF read. Switching accounts for one more decision interval plus subsequent safe recovery; the LMI method reserves a boundary margin for motion during that interval. Return to complex control requires reentering its permitted region. The unified method combines offline recovery guarantees with online reachable-set bounds. Its allocation-free, iterative algorithm trades computation budget for precision. Evaluation uses laptop computation and pendulum-model simulation; the 20 ms budget is **analysis runtime, not measured failsafe latency**. Model correctness remains an assumption. [Full text, §II-A, §II-B/Theorem 1, §III/Theorem 3, §IV, §V-B, §VI](https://stanleybak.com/papers/bak2014rtss.pdf).

## IMPLICATION — what our supervisor should copy

1. **Give STM32 final output authority.** Pi commands are proposals; STM32 selects the accepted command or a locally defined fallback without waiting for Linux or UART acknowledgments. For the course demonstrator, define fallback concretely as suppressing simulated actuation and asserting a failsafe indicator. Describe this as supervision inspired by System-Level Simplex; plant-level fail-operational safety would additionally require a validated backup controller and plant model. This keeps the experiment focused on OS timing and isolation. (Basis: source 1, §§2, 4.2.)
2. **Specify a small state machine:** start in `SAFE`; enter `RUN` only after explicit arming and valid fresh data; transition to latched `SAFE` on expired heartbeat/result deadlines or an invalid actionable command. Discard malformed frames without refreshing timers. Keep heartbeat liveness separate from result freshness: an alive bridge can repeatedly forward stale inference. Recovery requires explicit rearming after a documented healthy observation interval. (Basis: sources 1–3; recovery policy is our conservative choice.)
3. **Make validation bounded and deadlines independent of traffic.** Recommend framing/length/integrity checks, session and sequence checks, finite/range checks, and timestamp plausibility; duplicates must not renew result freshness. Use an MCU-local monotonic clock for silence deadlines. Source-age checks need clock alignment and an uncertainty margin. A periodic supervisor should outrank UART parsing/logging, with bounded ISR work, fixed buffers, and no blocking UART operation on the fallback path. These priority/framing proposals expose scheduling and IPC costs while preventing receive floods from delaying timeout checks. Exact framing, priorities, periods, and pinouts remain TBD.
4. **State the actual fault boundary.** Test stopped/killed bridge, stopped inference with bridge alive, delayed/duplicate/corrupt UART frames, CPU contention, and Pi reboot. Trust STM32 firmware/FreeRTOS, its clock, and the simulated output path; document shared power and electrical dependencies. CRC and sequence checks do not authenticate a malicious Pi or validate AI semantics. Copy S3A’s independent observation, but do not transplant its microsecond execution signature onto variable Linux inference.

## IMPLICATION — E4 latency measurement contract

Record **fault onset** `t_f`, **supervisor decision** `t_d`, and **observable fallback output** `t_s`. Report detection `t_d−t_f`, activation `t_s−t_d`, and total `t_s−t_f` separately. Capture an injection marker, decision marker, actual output, and preferably UART with one logic-analyzer clock; pin assignments are TBD. For process faults, bracket actual injection rather than equating shell-command launch with fault onset. Linux logs alone cannot establish timing through a freeze.

For silence timeout `W`, supervisor period `T`, maximum release/dispatch delay `J`, decision execution `C`, and output delay `A`, derive the conditional budget **`t_s−t_last_valid_rx ≤ W + T + J + C + A`**. Fault-to-output additionally depends on injection phase and any valid queued frames received after onset; measure/bound that backlog. Sweep injection phase and load, publish thresholds/baud/topology, sample count, median/p95/p99/maximum, false trips, and failures to transition. Observed maxima are not proven worst-case bounds. Hardware measurements remain outstanding.
