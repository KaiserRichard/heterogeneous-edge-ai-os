# R7 — ONNX Runtime on Raspberry Pi 5: workload spec

Research date: 2026-10-06. Context read: `PROJECT.md` §§1, 4–6, 8 and `AGENTS.md` in this worktree. AI supplies a Linux scheduling/contention workload; STM32 remains the UART supervisor. This document proposes experiments; no implementation or hardware validation was performed.

**Thread semantics:** [ORT Thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html), “Set number of intra-op threads,” “Set number of inter-op threads,” and “Thread spinning behavior”: intra-op parallelizes each operator and includes the calling thread; explicit counts disable ORT’s automatic worker affinity. Inter-op pools exist only with `ORT_PARALLEL`; sequential graph execution can still use multiple intra-op threads. Default spinning consumes CPU while waiting. The complete page was read, including affinity, NUMA and custom callbacks.

## IMPLICATION — proposed reproducible workload

- **Baseline:** MobileNetV2 `mobilenetv2-7.onnx`, FP32, batch 1, `[1,3,224,224]`, persistent Python ORT CPU session on Ubuntu 24.04 ARM64. Pin the tested ORT/NumPy versions, model URL and SHA-256, opset, input seed/data and preprocessing. Use a preallocated normalized tensor for isolated inference; report image preprocessing separately in pipeline experiments.
- **Threads:** sweep intra-op **1, 2, 4**, keep `ORT_SEQUENTIAL`, inter-op 1 and `ORT_ENABLE_ALL`. Start with spinning explicitly enabled to match published defaults; test disabled spinning separately. One session and one outstanding inference keep parallelism controlled. This exposes scheduling/resource-contention effects required by `PROJECT.md` §§5–6. Record every Linux thread’s affinity and scheduling policy when E2 changes them; configuring only the caller does not describe the worker pool.
- **Planning range:** provisionally **20–50 ms per warm inference** for V2 CPU ORT, rounded from the reported 4/1-thread means. This is a baseline sizing estimate, not a percentile interval, deadline guarantee or stressed bound. Two-thread latency, cold start, Ubuntu behavior and all contention tails require Pi measurement. Begin with a provisional 100 ms release period; calibrate before selecting E3 deadlines.
- **Measurement:** first reproduce 1,000 warmups/1,000 timed calls; then run three independent sustained trials per configuration under baseline and fixed stress profiles. Retain all measured spikes: report mean, p50/p95/p99/max, throughput and deadline misses. Log frequency/governor, cooling, temperature/throttling, kernel, RAM and stress parameters. Measure session startup separately; distinguish inference service time from release-to-completion and UART/MCU AoI.
- **Alternatives:** benchmark V3-Small and SqueezeNet 1.1 only after the V2 baseline; validate exported V3 operators, shape and outputs first. Keep precision/input/thread settings constant. Quantization is a separate treatment, since changing kernels would confound the OS comparison. All target performance remains **[unverified]** until run on the project Pi 5.
