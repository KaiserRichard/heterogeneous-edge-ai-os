## Supported kernel and installation

**SOURCE:** Canonical's [release announcement](https://ubuntu.com/blog/real-time-24-04), opening paragraphs and **“Launch Real-time Ubuntu on your silicon”**, identifies PREEMPT_RT on ARM64, upstream Linux **6.8**, and Pi 4/5 testing. Its Pro offering includes up to five free personal machines. The [release table](https://ubuntu.com/real-time/docs/reference/releases/), **“Ubuntu Server / Desktop”**, lists Noble 6.8 with `raspi`; its Noble HWE entry is generic only.

**SOURCE:** [Ubuntu Pro enable guide](https://ubuntu.com/pro-client/docs/en/latest/howtoguides/enable_realtime_kernel/), **“Attach your subscription,” “Make sure pro is up-to-date,” “Enable and install automatically”**, requires Pro attachment, updated client, the `raspi` variant and reboot. The [edition-specific enable guide](https://ubuntu.com/real-time/docs/how-to/enable-real-time-ubuntu/), **“Ubuntu Server / Desktop → Ubuntu 24.04 LTS … or earlier”**, directs Noble users to Pro; the adjacent main-archive instructions are for newer releases.

**IMPLICATION — proposed steps, on the Pi's existing Ubuntu Server 24.04 ARM64 installation:** Preserve a bootable stock image and record its versions first. Update the base system before establishing both comparison profiles; keep package versions stable during paired measurements. Run:

```sh
sudo apt update
sudo apt install ubuntu-pro-client
sudo pro attach                      # follow interactive subscription instructions
sudo pro enable realtime-kernel --variant=raspi
sudo reboot
```

After reconnecting, record:

```sh
uname -r
pro status
apt-cache policy linux-raspi-realtime
dpkg-query -W 'linux-image*raspi*'
cat /sys/kernel/realtime              # expect 1 if this interface is present
```

Require a running `*-raspi-realtime` kernel; service status alone does not prove it booted. Record `/boot/config-<uname -r>` and verify `CONFIG_PREEMPT_RT=y` if available.

**SOURCE:** [USN-8729-2](https://ubuntu.com/security/notices/USN-8729-2), **“Packages,” “Details,” “Update instructions”** (18 September 2026), documents security fixes and image `6.8.0-2053-raspi-realtime`, package version `6.8.0-2053.55`; reboot is required. ABI changes can require rebuilding external modules.

**IMPLICATION:** This is a dated, verified package example, **not a claim of the latest available ABI**. Record the actual installed/candidate versions and update date for every dataset; do not pin an old image merely to match this note.

## Known limitations and recovery

**SOURCE:** The Pro guide, **“Enable and install automatically”** and **“Install the hardware enablement (HWE) real-time kernel,”** warns that generic RT installation makes Pi systems unusable, shows Livepatch incompatibility, and excludes Pi from RT HWE. Its HWE version text differs from the newer release table; neither offers Noble Pi RT HWE.

**SOURCE:** [Switch from real-time to generic kernel](https://ubuntu.com/real-time/docs/how-to/switch-from-realtime-to-generic-kernel/), **“Check if other kernels are installed,” “Disable the real-time service on Pro,” “Remove the real-time kernel”**, says Pi fallback uses `linux-raspi`. Disabling Pro removes RT boot preference/update access but does not uninstall RT; removing the only kernel makes the system unbootable.

**IMPLICATION:** Do not use generic/HWE commands or assume `pro disable realtime-kernel` completes rollback. Check/install stock `linux-raspi`, follow the Pi-specific removal procedure, review selected packages, reboot and verify stock `uname -r`. Keep the saved stock image for recovery. UART/USB, fan operation and stress stability need smoke tests after switching. No Pi-5-specific RT/cpufreq regression is established by these sources; absence of such a finding is not proof of compatibility.

## CPU frequency and thermal controls for P3

**SOURCE:** Linux [CPU Performance Scaling](https://docs.kernel.org/admin-guide/pm/cpufreq.html), **“CPUFreq Policy Objects,” “Policy Interface in sysfs,” “Generic Scaling Governors → performance / schedutil”**, describes shared CPU policies, writable governor/limits, and requested versus actual frequency. `performance` requests the policy maximum; `schedutil` requests the allowed maximum on RT/deadline callbacks, potentially invoking the driver asynchronously. Neither removes thermal/power constraints. This is generic Linux documentation, not verification of Noble Pi defaults.

**SOURCE:** Raspberry Pi [frequency-management chapter](https://github.com/raspberrypi/documentation/blob/master/documentation/asciidoc/computers/raspberry-pi/frequency-management.adoc), **“Frequency management and thermal control,” “Use DVFS,” “Measure temperatures,” “Fan cases → Raspberry Pi 5 fans”**, documents progressive Arm throttling at 80–85°C and further throttling at 85°C, recommends active cooling, and describes fan thresholds/hysteresis. The Pi-4 DVFS modes/frequency steps are not Pi-5 setup instructions; `dvfs` configuration was removed on 5-series devices. Temperature measurement uses `vcgencmd measure_temp`.

**IMPLICATION — measurement plan:**

- Discover every `/sys/devices/system/cpu/cpufreq/policy*`; record driver, related CPUs, available/current governor, min/max limits and frequency. Do not assume a governor or one independent policy per core.
- For a controlled P2/P3 comparison, use the same governor and limits. If `performance` is available, save each original governor and set it through `scaling_governor` on both profiles; restore afterward. Keep P0 defaults as a separate baseline. This proposed control is **[unverified]** on our board.
- Use the same PSU, active cooler, fan settings and warm-up/cool-down protocol. Log temperature and frequency periodically alongside jitter/AoI; label `scaling_cur_freq` as potentially requested frequency, not guaranteed measured clock. Verify `vcgencmd` availability on Ubuntu **[unverified]**; identify thermal-zone names before using sysfs as an alternative.
- Flag thermally throttled runs separately from clean comparisons. Check UART delivery and fan response under sustained stress before accepting P3 results. Improved worst-case latency and unchanged throughput remain hypotheses requiring physical Pi/STM32 measurements.
