# R8 — Linux/MCU clock alignment: GPIO edge vs. UART round trip

## Recommendation

Use a four-timestamp round-trip exchange over the existing UART as the baseline
clock-alignment method. Keep the STM32 timer as the reference clock, and map
Linux `CLOCK_MONOTONIC_RAW` to STM32 timer ticks; do not set either system wall
clock. Use a shared GPIO edge only as an optional measurement/validation path,
unless the selected Raspberry Pi GPIO stack provides a hardware timestamp for
the edge. The latter availability on the project’s final Pi 5/UART topology is
**[unverified]**.

## Evidence

### SOURCE — round-trip exchange

RFC 4330, §5 (“SNTP Client Operations”), defines four timestamps: client
request transmit `T1`, server receive `T2`, server reply transmit `T3`, and
client reply receive `T4`. It computes round-trip delay and clock offset as:

`d = (T4 − T1) − (T3 − T2)`

`offset = ((T2 − T1) + (T3 − T4)) / 2`.

The section also says that the estimate assumes the exchange can characterize
propagation delay and that the client clock need not already be synchronized.
[RFC 4330 §5](https://datatracker.ietf.org/doc/html/rfc4330#section-5)

### SOURCE — GPIO/timer capture

ST AN4013, §2.3 (“Timer input capture mode”), states that STM32 input capture
stores the timer counter value after a transition on the input channel, with
selectable edge polarity, and points to STM32Cube `TIM_InputCapture` examples.
ST AN4776, §§2.2–2.3, adds an important limit: an asynchronous input is
resynchronized through two flip-flops, introducing a delay of at least two and
at most three timer-core clock cycles before the timer logic sees it. Thus GPIO
capture is hardware-timed, but not an ideal zero-delay observation.
[ST AN4013 §2.3](https://www.st.com/resource/en/application_note/dm00042534-gpio-operation-in-stm32-microcontroller-family-stmicroelectronics.pdf#page=14),
[ST AN4776 §§2.2–2.3](https://www.st.com/resource/en/application_note/an4776-how-to-use-generalpurpose-timer-peripheral-on-stm32-mcus-stmicroelectronics.pdf#page=20)

The Linux kernel HTE documentation describes the corresponding high-quality
case: a provider detects a GPIO state change, converts it to a nanosecond
timestamp, and delivers it to a consumer. This is a kernel hardware-timestamp
facility, not evidence that every Pi GPIO line has it enabled.
[Linux HTE, “More on the HTE timestamp data”](https://docs.kernel.org/driver-api/hte/hte.html#more-on-the-hte-timestamp-data)

### SOURCE — embedded precedents and limits

von Zengen et al., “A Sub-Microsecond Clock Synchronization Protocol for
Wireless Industrial Monitoring and Control Networks,” §III, uses precise
hardware packet timestamps and a four-event PTP-style exchange; §III-B estimates
drift from successive synchronization intervals. In §IV, Node0 toggles a GPIO
at 1 Hz, all STM32 nodes timestamp the interrupt, and UART carries timestamps to
a logging PC; the wired GPIO was deliberately used to minimize trigger delay
and jitter. Their §IV-B reports mean absolute offsets of 0.54/0.33 µs without
drift compensation, and §IV-C reports 0.19/0.22 µs with compensation. Those
numbers are results for their timestamping radio and test setup, not a promise
for Linux userspace plus UART.
[Paper §§III–IV](https://www.ibr.cs.tu-bs.de/oa/vonzengen_ICIT2017.pdf#page=3)

Schmidt et al., “Time-Triggered Communication with UARTs,” §§2.2–2.3, identifies
UART send jitter (up to one baud period), oscillator drift, and baud-rate
quantization as timing sources; §3 derives communication bounds from frame
length and baud-rate mismatch. This is directly relevant to the project’s
UART-only link.
[Paper §§2–3](https://mobile.aau.at/~welmenre/papers/2002/rr-19-2001.pdf#page=2)

## IMPLICATION — method specification

1. **Baseline protocol.** Linux sends a sync request containing sequence number
   and `T1` immediately before the write. STM32 timestamps RX at the UART
   receive boundary (`T2`), timestamps its response transmit boundary (`T3`),
   and echoes the sequence plus `T1..T3`. Linux timestamps response receipt
   (`T4`). Compute the RFC 4330 offset and delay. Collect a burst, reject bad
   CRC/sequence samples, and select the minimum-delay sample or a low-delay
   robust median; retain delay and residual as quality indicators.

2. **Accuracy expectation.** The RFC equations remove symmetric link delay,
   but they cannot remove asymmetric UART serialization, Linux scheduling and
   read/write wake-up latency, or timestamp placement error. At 115200 baud,
   one 10-bit UART character occupies about 86.8 µs; therefore a userspace
   software-timestamped exchange should be specified initially as a
   **sub-millisecond engineering target**, not sub-microsecond accuracy. The
   exact bound is **[unverified]** until measured on the Pi 5 under idle and
   stress conditions. Report median, p95/p99, worst observed offset residual,
   and drift between syncs rather than one accuracy claim.

3. **GPIO profile.** If a spare GPIO is wired, configure an STM32 timer input
   capture and use the edge as an external ground-truth marker. At a 180 MHz
   timer clock, one counter tick is nominally 5.56 ns, but ST’s documented
   two-to-three-cycle input resynchronizer and board signal delay remain. A
   Linux userspace GPIO toggle timestamp is not the physical edge timestamp;
   it includes driver and scheduling delay. Promote GPIO to the primary method
   only if Linux supplies a verified hardware edge timestamp (HTE/PHC-like
   path) and the wiring/pinout is frozen. The exact STM32F446 timer clock and
   selected pin mapping are still **[unverified]** because PROJECT.md marks
   them TBD.

4. **Drift handling.** Estimate frequency ratio from successive sync points and
   apply a linear offset-plus-rate mapping between Linux monotonic time and
   STM32 ticks. Re-sync periodically; the embedded precedent shows that even
   sub-microsecond initial alignment degrades with oscillator drift unless the
   rate is compensated.

This keeps the experiment within the project’s UART-only architecture while
making the STM32 an independent timing observer. Hardware validation on the
actual Raspberry Pi 5, STM32F446RE, wiring, baud rate, and Linux load profile
is required before claiming the measured accuracy.
