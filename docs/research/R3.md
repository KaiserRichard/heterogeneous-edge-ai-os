- [§4.2](https://arxiv.org/html/2604.19275v2#S4.SS2), [§5](https://arxiv.org/html/2604.19275v2#S5): `isolcpus=2,3`; control/core 2, supporting threads/core 3; memory locking; `CLOCK_MONOTONIC`/`clock_nanosleep`; period=deadline=4 ms; 10,000 iterations/configuration; `sched_rt_runtime_us=-1`.

## IMPLICATION — reusable E1/E2 checklist

These are project recommendations, not additional results from the paper.

- [ ] **Record the actual platform.** On the Linux target, log board/RAM, OS, full kernel/package versions, tool versions, boot arguments, governor, observed frequency, temperature, throttling, swap, services, RT budget, affinity, and workload thread count. Our Pi has 4 GB ([PROJECT.md §2](../../PROJECT.md)); choose and log a total VM allocation that fits it. Verify frequency throughout the run instead of assuming the governor enforces a fixed clock. Keep thermal conditions comparable across profiles.
- [ ] **E1: isolate stressor effects.** Compare P0 idle with CPU-only, VM-only, cache-only, I/O-only, then a combined profile. Reuse the paper's compute/VM/kernel-stress categories, but label chosen commands as our implementation: `cpu-matrix` is its descriptive label, not a verified CLI recipe. Record worker counts, allocation bytes, methods, CPU masks, duration, and measured load. Separate same-core CPU competition from neighboring-core memory contention. Resolve exact flags in R5; I/O stress is an extension to this paper.
- [ ] **E2: isolate tuning effects.** Compare OTHER and FIFO on the same stock kernel, initially using priority 50 as a documented experimental choice. Keep load and workload identical; add affinity, memory locking/preallocation, and CPU quota individually before testing the combined P1 profile. Report changes to both inference and bridge behavior. Do not silently import priority 99, boot isolation, or disabled RT throttling; preserve the project's configured RT budget and record it ([SYSTEM_OVERVIEW.md §2](../SYSTEM_OVERVIEW.md)).
- [ ] **Control the kernel comparison.** The proposed P3 includes P2's latest-value buffering, whereas P1 does not ([SYSTEM_OVERVIEW.md §3](../SYSTEM_OVERVIEW.md)). P1→P3 therefore cannot identify a kernel-only benefit. Add a matched P2→P3 comparison, or hold buffering identical in a separately labeled kernel comparison. [PROJECT.md §7](../../PROJECT.md) permits packaged P3; [AGENTS.md §3](../../AGENTS.md) still prohibits PREEMPT_RT. Record this policy conflict before any future setup; this ticket makes no installation or architecture change.
- [ ] **Define timestamps before measuring.** Log scheduled release, actual execution start, inference completion, bridge readiness/start, and UART submission separately. Report release lateness, ready-to-running delay, execution duration, and data-path delay with explicit formulas. For a periodic probe, use absolute monotonic releases to avoid drift. Measure UART/MCU arrival separately: a Linux write timestamp does not establish physical delivery or end-to-end freshness.
- [ ] **Use diagnostics as companion measurements.** Proposed `cyclictest`: one pinned thread, documented policy/priority, memory lock, 4000 µs interval, and 10,000 samples as an initial comparable exposure. Proposed `rtla timerlat`: separate diagnostic runs to distinguish timer IRQ and thread latency; check stock-kernel/tool support first. Commands and availability on our Pi remain **[unverified]**; neither tool reproduces the inference/UART path. For outliers, collect available timer/IRQ and scheduler trace events with `perf`, retaining raw traces and checking dropped events and tracing overhead.
- [ ] **Repeat and report tails.** At 250 Hz, 10,000 releases represent about 40 s; use multiple independent repetitions and longer stress exposures to investigate rare stalls. Save raw samples and per-run P50/P95/P99, maximum, sample count, deadline-miss numerator/denominator, and time series. Define deadline misses using completion relative to release plus deadline, not dispatch jitter alone. Mark failed/OOM/throttled runs explicitly.

**Interpretation limits:** Treat measured maxima as observations, not proven worst-case bounds. The FIFO-99 maximum pair gives an 87.9% reduction; it does not describe every policy or percentile. Test the memory-contention hypothesis with separate stressors and counters where available. Keep the STM32 supervisor: scheduler-only evidence cannot establish UART timing or our F446RE's determinism, and the paper's literature-based MCU comparison is **[unverified]** here. All proposed target measurements require Pi/STM32 verification; none were run on macOS.
